## 1. 本次变更范围

本次从正式应用完整移除了模型声明核对、自动模型采集、转发器、Codex 路由配置管理及独立联网探测功能，不是仅隐藏界面。删除了 18 个专用源码、脚本、测试和文档文件；其余共享文件中的类型、命令、事件、样式、依赖和启动/退出逻辑也已清理。

保留的核心功能包括 Input / Cached / Output、缓存命中率、总 token 汇总、项目/会话/日期筛选、父子会话归属、日志模型名称与 reasoning effort、列宽调整、跟随最新记录，以及复制会话 ID。

模型列明确标为“日志模型”。它表示本地日志记录的名称，不认证真实后端模型，不推断账号风控或模型能力。应用读取会话 JSONL 时可能经过包含正文的记录，但只在应用数据模型中保留用量和展示元数据；不能将此描述为完全不读取正文所在文件。

生产入口现在只注册 `get_snapshot`，并发送 token 监控相关事件。剪贴板仍只授予写文本权限。Python 不再是应用运行或测试的依赖，直接的 `toml_edit` 依赖已删除；Tauri 自身仍可能通过传递依赖使用 TOML 相关库。

出处：[后端入口](../src-tauri/src/lib.rs)、[监控核心](../src-tauri/src/monitor.rs)、[前端](../src/App.tsx)、[权限](../src-tauri/capabilities/default.json)、[Rust 依赖](../src-tauri/Cargo.toml)。

## 5. 后续改进建议

以下是基于当前代码的工程建议，不是已实现功能。优先保证统计含义和数据完整性，再扩展展示能力。

### 优先级一：统一记录保留策略和统计覆盖范围

**代码事实：** `monitor.rs` 的 `MAX_RECORDS` 为 50,000，`consume_bytes()` 只裁剪调用数组；`seen_ids` 没有对应裁剪。前端 `App.tsx` 对每条事件追加/更新 Map，没有同步淘汰协议。首次加载的文件遍历也没有时间顺序保证，数组头部淘汰不等于淘汰最早时间的记录。

**风险推导：** 长时间运行后，前端、后端快照和去重缓存可能持有不同范围的数据；重新打开应用后，筛选汇总可能变化。去重缓存和前端数据也可能持续增长。这些不能仅靠把上限调大解决。

**建议：** 先明确“加载窗口总量”还是“完整历史总量”。统一按时间和稳定 ID 管理保留范围；后端向前端发送淘汰信息，或改为分页查询。界面显示覆盖时间、已加载条数和截断状态。全历史统计可考虑仅保存元数据的本地索引，而不是无限增长的内存集合。

**验收方向：** 用超过 100,000 条的乱序多文件数据，比较首次加载、持续追加、归档迁移和重启后的统计结果；验证明确的内存上界。

出处：`src-tauri/src/monitor.rs` 的 `Inner`、`consume_bytes()`、`list_jsonl()`；`src/App.tsx` 的调用 Map 与 summary。

### 优先级一：大日志读取预算与大表格性能

**代码事实：** 每轮扫描递归枚举目录并重建目录信息，扫描期间持有共享锁。`sync_file()` 虽限制到当时文件长度，但仍可能一次读完很大的剩余区间；`consume_bytes()` 对行另行复制，未换行尾部没有硬性大小限制。会话索引变化时整体 `read_to_string()`。前端每条事件复制 Map，筛选后排序，并用 `rows.map()` 渲染全部记录。

**风险推导：** 大量历史日志、超长 JSON 行和密集新调用会增加内存峰值、启动等待及界面工作量；当前测试通过不代表已完成性能验收。

**建议：** 为每个文件和每轮扫描设置读取预算、超长行策略与公平推进机制；减少全文 Value 解析和复制，增量读取索引。引入批量事件与表格虚拟化（只渲染可见行）。文件变更通知应有轮询恢复机制，而不是完全依赖单一通知路径。

**验收方向：** 对 1,000 / 10,000 / 50,000 条可见记录和不同日志体积测量首屏时间、扫描耗时、内存、事件延迟与滚动流畅度。本次未提供未经测量的性能倍数。

出处：`monitor.rs` 的 `scan()`、`sync_file()`、`consume_bytes()`、`sync_session_index()`；`App.tsx` 的事件处理、`rows` 与表格渲染。

### 优先级二：日志兼容性、异常数据和时间语义

**代码事实：** 目前仅把 `token_usage_record` 作为逐调用用量；旧式 `event_msg.token_count` 不作为逐调用数据。`u64v()` 对缺失、类型不符等情况返回 0；缺失时间戳会回退到当前时间；缺失响应 ID 时由部分字段拼接 ID。前端排序比较原始时间戳字符串，日期筛选则解析成时间。

**风险推导：** 不兼容的日志可能表现为“零调用”而不是清楚的格式提示。无效数值与真实零值无法区分。不同时间偏移的字符串排序可能与实际时间顺序不一致，缺失 ID 的重复判定也有局限。

**建议：** 为明确支持的日志版本建立去敏固定样本和版本兼容表；不要把累计用量直接当作逐次调用。区分缺失/无效/零，增加异常记录计数；保留来源与质量状态。排序与筛选使用统一时间语义，缺失时间不应伪装为真实发生时间。对无响应 ID 的来源位置或稳定指纹设计明确规则。

**验收方向：** 测试混合时区、跨日/夏令时边界、缺失字段、超大数值、相同时间多调用、缓存量大于输入量及不同日志结构。

出处：`monitor.rs` 的 `process_row()`、`normalize_usage()`、`u64v()`；`App.tsx` 的排序和 `dateBoundary()`。

### 优先级二：让 Live 和错误提示反映持续运行状态

**代码事实：** `Live` 在初始快照成功后设置，尚未根据后续心跳超时自动变更。目录不可读、文件打开失败等路径多为直接跳过；界面错误数主要体现会话 JSON 解析失败，不能覆盖所有 I/O 和格式问题。

**建议：** 展示最后成功扫描时间、扫描耗时、不可读/不兼容文件数和待处理队列，区分初始化、无兼容日志、数据过期、部分失败和正常运行。提供明确的路径权限提示与重试操作。诊断导出只包含必要元数据，并提示路径/会话标识的隐私风险。

**验收方向：** 模拟目录消失、权限不足、索引坏行、后台停止推送和恢复，确认界面不会持续把失败显示成正常。

出处：`src-tauri/src/lib.rs` 的轮询；`monitor.rs` 的 I/O 错误路径；`App.tsx` 的 `live` 状态。

### 优先级二：可复现构建与原生桌面回归

**代码事实：** 当前项目仍沿用忽略 `package-lock.json` 和 `src-tauri/Cargo.lock` 的策略。直接依赖固定版本并不能锁定所有传递依赖。CI 未固定 Rust 工具链；本次浏览器测试不是原生 WebKit 测试。

**建议：** 将锁文件纳入版本控制，使用 `npm ci` 和 Cargo 的 locked 模式；固定可验证的 Rust 工具链，并增加最低版本验证。在 Linux 图形环境补原生窗口启动、IPC、剪贴板及关闭退出用例。保留本次合成回归，并补长期运行与故障恢复测试；第三方依赖漏洞检查应覆盖 Rust 和前端两个依赖树。

出处：[忽略规则](../.gitignore)、[CI](../.github/workflows/ci.yml)、[测试配置](../playwright.config.ts)。

### 优先级三：在统计可靠之后增强使用效率

可增加常用日期范围、按项目/会话/日志模型汇总、可选 CSV/JSON 元数据导出，以及紧凑列宽和列显隐预设。900 像素宽度下目前需要横向滚动才能查看后面的 token 列，可提供以用量为主的窄屏布局。任何历史汇总都应说明覆盖范围，任何导出都应尽量少包含路径和会话标识。

不建议再引入仅凭不透明响应字段猜测账号风控、模型身份或能力的默认功能。
